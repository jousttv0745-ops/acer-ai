我的 Claude 工作法

我用 Claude 做過六種工作：設定環境、競品分析、產品推薦、提案簡報、規格文件、追蹤 AI 新訊。每一種都整理成一條可以重複跑的流程。我的原則是：同一件事做到第二次，就把它做成範本。

01 · SETUP

先花一次力氣設定好，之後每次對話都用得到

預設的 Claude 每次開新對話都不記得我是誰、要什麼格式、做事有什麼規矩。我把這些寫進檔案和工具，只要設定一次。

CLAUDE.md：寫給 AI 的工作守則

每次對話都會自動載入。內容包括我的角色、預設技術環境、輸出格式，以及 14 條品質守則。

  • 固定輸出順序：先給可以直接用的產出，再說明
  • 資料不夠就停下來列出缺什麼，不用假設硬補
  • 引用的數字要標來源，沒來源就標「未驗證」
  • 用 /plan /diff /snap 這類短指令直接切換模式

Superpowers：讓 Claude 照工程流程做事

Superpowers 是一套 skill 外掛，強迫 Claude 按固定階段工作，不會一收到需求就開始寫。

  • brainstorm：先問清楚需求
  • write plan：拆成小步驟，我確認後才動手
  • execute：交給 subagent 逐步執行
  • verify：跑過驗證才能說「完成」

Skill 與 MCP：把 SOP 和資料接進來

重複的任務包成 skill，用斜線指令叫出來，例如 /competitive-analysis 做競品分析。再用 connector 接上 Google Drive、Gmail、Figma、GitHub、ClickUp，Claude 就能直接讀寫資料，我不用再手動複製貼上。完整清單見下方。

手機遠端控制：離開電腦也能繼續跑

在專案資料夾執行 claude remote-control，或在正在跑的 session 裡輸入 /remote-control。之後用手機上的 Claude app 就能接手同一個 session：看進度、回覆問題、下一步指令。我的提案簡報就是用這種方式，離開電腦後繼續修改。

工作流程
  1. 寫 CLAUDE.md角色、環境、輸出格式、品質守則、觸發詞。每次覺得「又要講一遍」就補進去。
  2. 裝 Superpowers讓複雜任務一定先釐清需求、出計劃、確認，再動手。
  3. 接 MCP connectorDrive、Gmail、Figma、GitHub、ClickUp。資料來源在哪，就接到哪。
  4. 重複的任務包成 skill同一種任務做過兩次，就用 skill-creator 整理成 skill。
  5. 開 Remote Control長任務在電腦上跑，人離開座位後用手機接手。

Take away

最值得先做的兩件事：寫 CLAUDE.md、裝 Superpowers。

CLAUDE.md 讓你不用每次重新交代規矩。Superpowers 讓 Claude 先想清楚再動手。這兩件設定完，後面每一種工作流程的品質都會提高。

02 · BENCHMARK

影片競品分析：從社群找齊官方影片，再逐格拆解

ASUS 同一波 AI 產品行銷，在 Facebook 和 YouTube 用了好幾種完全不同的影片格式。一支一支看只會留下印象，所以我請 Claude 直接讀影片頁和影片檔，逐格抽樣，拆成可以並排比較的拆片表。

工作流程
  1. 爬蟲找影片、列清單在 Google 和社群平台找 ASUS Zenni Claw 的宣傳影片，以官網和官方社群為主，KOL 的開箱或使用心得也一起抓。清單欄位：發布單位、標題、連結、社群反響。
  2. 讀頁面數據由瀏覽器直接讀影片頁：發布日、觀看、讚數、留言、貼文文案。片長用 video 元素回報的實際秒數，不用頁面上四捨五入的數字。
  3. 逐格抽樣用 canvas 每 0.6–4 秒抽一格，拼成影格條，再依畫面切出時間軸：主持人出鏡、實拍、動態圖卡、UI 錄影、尾卡。
  4. 用 skill 整理成拆片表第二個 prompt 叫出 /competitive-analysis skill。每支影片都填同一組 10 個比較項：發布、長度、畫幅、觀看／互動、文案策略、拍攝形式、字幕／字卡、剪輯節奏、結尾 CTA、適合任務。
  5. 寫橫向觀察，標出限制例如「Facebook 賣情境，YouTube 賣規格」、「互動率打平，但日均觀看差 9 倍，差在片長」。跨平台不能直接比的數字，一律標「未驗證」。
瀏覽器讀取canvas 抽格拆片表Artifact 發佈

成品：《Zenni Claw 影片拆片表》，5 支 ASUS AI 社群影片 × 10 個比較項，外加逐支分鏡與 9 條橫向觀察。

Take away

先固定比較項再拆片，每條觀察都要能對回一段影片或一個數字。

數據要寫清楚來源和限制。像「互動率高」這種數字，如果跨平台、跨粉專，就不能拿來證明哪種內容比較好。

03 · RECOMMEND

推薦機制：先算出每台電腦能跑哪些 AI app，再依情境推薦

AI 功能有硬體門檻，但官網只放一長串相容清單，使用者不知道該買哪一台。我把設定檔、官網需求和商城商品三個來源接起來，讓推薦結果可以一路追回規格。

Input

AIS 設定檔 App-list.json：每個 app 的規格需求與安裝檢查

Qubi Claw 官網：雲端／內顯本地 AI／RTX 5090 三級需求

Acer 官方商城：正在販售的 345 台電腦與完整規格

Output

App 規格表：9 個 AIS app 各自的硬體條件

商品相容對照表：345 台 × 9 個 app，加上 Qubi Claw 等級

Final

情境推薦：每個情境給出首選、第二推薦、CP 值最高三個位置

工作流程
  1. 把設定檔整理成 App 規格表設定檔裡給人看的說明文字（RequirementDetails）轉成「規格需求」欄；程式的安裝檢查（SystemRequirement）轉成「安裝時檢查」欄。Qubi Claw 不在設定檔內，另依官網需求分成 0～3 級。
  2. 逐台比對商城商品讀每台商品頁的 CPU 世代、RAM、顯卡與 VRAM、螢幕，對每個 app 判定：可裝、寬判才可裝、不可裝。345 台裡有 324 台至少能裝一個 app。
  3. 從情境找關鍵 app例如商務看 Meeting Assistant＋AI Agent，創意看 Drawing Assistant，遊戲改看獨顯。
  4. 定篩選門檻和排序商務：兩個 app 都能裝、有庫存的筆電 57 台，依 Qubi Claw 等級 → 重量 → 商務配備 → 續航 → 價格排序。每個情境各有一套排序規則。
  5. 放進 mockup 的推薦卡三個情境各選出首選、第二推薦、CP 值最高，直接變成「找到你的 AI 搭檔」推薦卡，並標註商城資料的日期。
App-list.json商城商品頁相容對照表排序規則
Take away

推薦要先算得出來，才講得出來：每一張推薦卡都能追回設定檔和商品規格。

Input 和 Output 分開整理。商城資料或 app 需求一變，重跑一次比對，推薦結果就跟著更新。規格沒寫到的新世代標成「寬判」，不計分，不硬猜。

04 · PROPOSAL

Mockup 和線上簡報：做成可以點的網頁，用 git 管理版本

靜態投影片講不清楚動態的 hero 和互動效果，改版時也很難知道每一版改了什麼。所以我把提案直接做成網頁：mockup 是真的可以動的 HTML，簡報是一個範本引擎。

簡報範本化：引擎和內容分開

engine/deck.js 負責畫面和換頁，裡面沒有任何專案專屬的內容。每份提案只要改 deck.config.js：章節、頁面、要框出的重點區域，全部寫在設定檔裡。

另外寫了 check-config.js 檢查設定：檔案是否存在、框選範圍有沒有超出頁面、規格欄位有沒有漏填。

Mockup：多個方向一起比較

Hero 一次做五個方向（A–E），加上一個比較頁，大家可以直接點開來看。角色動畫用 three.js 做成可以操作的 3D 模型，提供走路、揮手、點頭、跳躍等動作。

Claude 透過 Figma MCP 直接讀寫 Figma：可以把設計稿轉成 HTML，也可以把確定的 HTML 畫面推回 Figma 給設計師接手。

工作流程
  1. 在本機開發用 .claude/launch.json 啟動本機伺服器，Claude 改完就能馬上預覽。
  2. 每次修改都 commit每個 commit 寫清楚改了什麼、為什麼改。改壞了隨時可以退回上一版。
  3. 大改版就開新資料夾v3/ 和舊版並存，舊連結不會失效。圖片網址加版本參數，避免瀏覽器讀到舊的快取。
  4. 推上 GitHub Pagesgit push 之後網站自動更新，把連結給大家就能看最新版本，手機會自動切成輕量模式。
  5. 內部筆記不公開設計筆記放在 docs/，並加進 .gitignore，不會跟著發佈出去。
HTML mockupthree.jsFigma MCPgitGitHub PagesRemote Control
Take away

提案本身就是可以操作的原型，而簡報是一個可以重複使用的範本。

換下一個專案時，引擎和檢查工具直接沿用，只要換設定檔和內容。用 git 保留每一版，客戶問「上一版是什麼樣子」時，隨時都答得出來。

05 · REVERSE SPEC

逆向工程：從安裝檔重建產品需求文件

Qubi 已經上市，卻沒有一份完整的規格文件，產品是從 Acer AI Agent 演變來的，很多決定沒有留下紀錄。我請 Claude 拆解 Qubi 的安裝檔，把程式裡看得到的東西整理成一份 PRD，並且誠實標出哪些是證據、哪些是推論。

工作流程
  1. 讀取本機安裝的 Qubi用 Superpowers 的 brainstorming 先談好範圍和產出物，再開始讀。以 1.9.1000 為基準，另外拆 1.8.2000 的安裝檔來比對。從執行檔名、通訊管道、登錄檔路徑、語系字串、產品目錄文字、介面元件，找出功能和設定。
  2. 每條發現都登錄成證據每個發現都編號（E001、E002…）記進 qubi-evidence.csv，寫清楚出自哪個檔案。例如執行檔名仍叫 Acer_AI_Agent_Widget.exe，證明它的前身是 Acer AI Agent。
  3. 整理成功能矩陣拆出 95 項功能，每一項都寫上觸發入口、相依模組和證據編號，存成 qubi-feature-matrix.xlsx。
  4. 用四種證據等級寫 PRD每一章都標等級：【事實】有程式或檔案證據、【產品團隊確認】、【推論】由設計取捨推得、【待確認】需要產品團隊補。「為什麼做、為誰做」讀不出來，就老實標成推論。
  5. 比對版本，列出待確認清單比較 1.8 和 1.9 的差異，推出產品的兩條演進方向。沒有反編譯的元件、查不到證據的流程，全部列成待確認清單，交給產品團隊校正。
/superpowers:brainstorming安裝檔拆解版本比對qubi-evidence.csvqubi-feature-matrix.xlsxqubi-spec.md

成品：《Acer Qubi 產品需求文件》工作版，共 10 章：概述、問題、目標使用者、使用場景、功能需求（FR-1～FR-12）、非功能需求、法規符合性、使用者旅程、與其他 Acer AI 產品的關係、版本演進。另附系統規格、功能矩陣、證據對照三份檔案。

Take away

逆向工程最重要的不是讀出多少東西，而是分清楚哪些是事實、哪些是推論。

每一句都標證據等級，並且能追回證據編號。這樣產品團隊只要校正【推論】和【待確認】的段落，不用從頭檢查整份文件。

06 · CROSS-CHECK

AI 新訊：ChatGPT 排程收集，兩個模型互相查核

AI agent 的消息一週就變一次，自己追不完，只看單一模型的整理又怕有錯。所以一邊負責定期收集，兩邊再互相挑錯。

工作流程
  1. ChatGPT 排程收集設定排程任務，定期整理 AI agent 相關新訊，產出摘要。
  2. 放進共用資料夾兩個模型共用本機上的同一個資料夾。摘要、查證結果、意見都寫成檔案放在裡面，兩邊讀的是同一份資料。
  3. Claude 查證並補充Claude 讀資料夾裡的摘要，逐條找第二個來源，標出互相衝突和查不到出處的內容，結果寫回資料夾。
  4. ChatGPT 回頭互評ChatGPT 讀 Claude 的查證結果，反駁或補充。兩邊都同意的才列為結論。需要我判斷的地方，我會手動貼過去討論。
  5. 篩出和工作相關的行動最後由 Claude 挑出和手上專案有關的項目，轉成待辦或 skill 的更新。
ChatGPT 排程任務本機共用資料夾Claude雙向互評
Take away

一個模型負責收集，兩個模型互相挑錯。

單一模型整理的資訊可能有幻覺，讓另一個模型挑錯最便宜。雙方都有來源、也都同意的內容，我才拿來用。

總結

把每一套工作流程做成範本

上面六個流程有一個共通點：做第一次時順手留下可以重複用的東西，第二次就從範本開始。

CLAUDE.md

對話規則的範本。每次開新對話都自動套用。

拆片表

影片競品分析的範本。固定 10 個比較項，新影片照填。

Input → Output 對照表

推薦機制的範本。商城或需求一變，重跑比對就更新。

線上簡報引擎

提案的範本。換專案時只換設定檔和內容。

證據等級 PRD

規格文件的範本。分四個證據等級，每一句都能追回證據編號。

共用資料夾

新訊查核的範本。兩個模型讀寫同一批檔案。

  • 01每次要重新交代的規矩，就寫進 CLAUDE.md。
  • 02同一件事做到第二次，就做成範本或 skill。
  • 03AI 說完成不算完成，要另外跑一次驗證，或請另一個模型檢查。
  • 04開場先問規劃，不直接要答案：說清楚目標、附上資料來源，最後問「你會怎麼規劃？」
